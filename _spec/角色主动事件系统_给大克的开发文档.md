# 开发任务：角色主动事件系统（关系驱动的主动调度）

> 写给大克（Claude Code）。橘子不写代码，这份文档是完整需求规格，请你按此实现。
> 目标用一句话说：**让角色会因为自己的原因、在合适的时机主动来找玩家**，而不是只能等玩家去找他们。

---

## 一、需求背景与设计哲学（务必先理解，再动手）

现状：游戏里的人物交互是**玩家发起**的——玩家点"主动找他聊聊"、送礼、追问线索，角色被动响应。

橘子要的不是"换个地方做 AI 角色扮演"，而是**让世界有"惦记玩家"的主动性**：某个角色会自己冒出来找玩家说话/约玩家做事。

这个"主动"必须同时满足三条，缺一条就会变味：

1. **有原因**：角色来找你，必须挂在你俩的真实历史上（`world.memory` 里的某条），不能是凭空随机弹窗。例：因为前几天玩家帮过纳威，纳威攒够勇气来道谢。
2. **有节制**：主动事件必须低频、有冷却、按关系深浅给不同概率。关系浅的几乎不会来；关系深的也只是偶尔来。**一天最多 1～2 个角色主动来找玩家**。频繁触发 = 骚扰 = 毁沉浸感。这是最容易做坏的地方，务必克制。
3. **不可预测**：玩家不能精确算出"我做了X，第二天必定有人来"。要有概率、有延迟、有"多个候选竞争名额"的随机性。

**重要：本系统的"主动性"来自本地调度逻辑，不来自 AI。** AI（若启用）只负责把"已经被决定要发生的相遇"演得更鲜活。没有 AI / 没网 / 没填 key 时，系统用预写文本照常运行。这是双轨设计（见第六节）。

## 三、文件结构（橘子的要求：一角色一文件，好维护）

新建 `characters/` 目录：

```
characters/
  _registry.js        ← 汇总导出所有角色对象，供调度器遍历
  harry.js            ← 单个角色：静态人设 + 主动事件定义
  neville.js
  draco.js
  ...（每个角色一个文件）
proactive-scheduler.js  ← 主动事件调度器（核心新增逻辑）
```

### 关键原则：静态与动态分离
- **角色文件里只放静态内容**（手写、不变）：人设、背景、说话口吻、主动事件模板、预写对话文本。
- **动态状态绝不进角色文件**，必须留在存档 `world`/`affinity` 里：当前好感、memory、冷却记录、已触发 flag。
- 理由：角色文件应可被随意编辑/由不同 AI 分工撰写，而存档数据跟着玩家走。混在一起会让存档逻辑崩坏。

## 四、角色文件的数据结构

每个 `characters/xxx.js` 导出一个对象。在现有 affinity 字段（tiers/encounters/story/letter）基础上，**新增 `persona` 和 `proactive` 两块**：

```js
// characters/neville.js
export default {
  key: 'neville',
  name: '纳威·隆巴顿',
  house: '格兰芬多',

  // —— 新增1：人设（供 AI 模式当 system prompt 的素材；本地模式可不用）——
  persona: {
    summary: '胆小、笨拙但善良的格兰芬多新生，怕魔药课，怕斯内普，养了只蟾蜍叫莱福。',
    speechStyle: '说话犹豫、爱用省略号、紧张时会结巴，但谈到草药会突然流利。',
    facts: [   // 关键设定，AI 扮演时不能违背
      '1991年入学，与哈利同届',
      '奶奶严厉，对他期望高',
      '不擅长除草药学外的大部分课程'
    ]
  },

  // —— 新增2：主动事件（核心）——
  // 调度器会遍历这个数组，判断今天纳威要不要主动来找玩家
  proactive: [
    {
      id: 'neville_thanks_rescue',          // 唯一ID，用于冷却和去重
      // 触发条件（调度器据此判断是否进候选池）
      require: {
        minTier: 2,                          // 好感至少到第2阶
        memoryTag: 'helped_neville',         // world.memory 里必须有这个标记的条目（=有原因）
        cooldownDays: 7,                      // 触发后7天内不再触发同一事件
        chance: 0.3,                          // 进了候选池后，掷骰命中概率
        oneTime: false                        // 是否一辈子只触发一次
      },
      // 本地预写内容（保底，无AI时直接用这套）
      opening: '纳威在公共休息室门口站了一会儿，手里攥着一小包东西。"那个……上次……谢谢你。我、我没什么好给的，这是奶奶寄来的糖。"',
      choices: [
        { label: '收下，说不客气', delta: 2, response: '他松了口气，笑得有点傻。"那……那我先走了。"', addMemory: 'neville_gave_candy' },
        { label: '让他不用客气，糖留着自己吃', delta: 3, response: '"可、可是……" 他还是把糖塞给了你就跑了。' }
      ],
      // AI 模式用的种子（启用AI时，把这段+persona+相关memory喂给AI生成对话；不填则AI模式回退用opening）
      aiSeed: '纳威鼓起勇气来感谢玩家上次的帮助，他很紧张，带了奶奶寄的糖作为谢礼。'
    }
    // ……可以定义多个主动事件
  ]
};
```

`memoryTag` 的来源：当玩家做了某事（如帮纳威解围），现有代码调用 `rememberWorldEvent` 时，给那条 memory 加一个 `tag` 字段（如 `tag:'helped_neville'`）。调度器靠扫描这个 tag 来确认"有没有原因"。**这一步需要你在相关的"玩家行为产生memory"的地方补上 tag 标注。**

## 五、调度器逻辑 `proactive-scheduler.js`

导出一个函数 `runProactiveScheduler()`，在 `nextDay()` 末尾的 setTimeout 里调用（与 triggerDailyBrief 并排）。

伪代码逻辑：

```
function runProactiveScheduler():
    data = getSave()
    today = data.time.currentDate
    allCharacters = 从 _registry.js 拿到所有角色

    candidates = []   // 候选池

    for 每个 character in allCharacters:
        for 每个 ev in character.proactive:
            req = ev.require
            // 逐条硬性筛选（任一不满足就跳过）
            if getTier(character.key) < req.minTier: continue
            if req.oneTime 且 已触发过(flag): continue
            if 在冷却期内(上次触发 + cooldownDays > today): continue
            if req.memoryTag 且 world.memory 里没有带该tag的条目: continue   // ← 保证"有原因"
            // 通过硬性条件，进候选池，记下它的概率
            candidates.push({ character, ev, chance: req.chance })

    if candidates 为空: return   // 今天没人来，很正常

    // —— 节制控制：限制今日主动事件总量 ——
    maxToday = 1   // 默认一天最多1个；可设计为关系网越大上限略升，但建议封顶2
    triggered = 0
    打乱 candidates 顺序   // 保证公平+不可预测

    for 每个 cand in candidates:
        if triggered >= maxToday: break
        if random() < cand.chance:        // 掷骰
            投放主动事件(cand.character, cand.ev)
            记录冷却(setFlag: lastTriggered date)
            triggered++

function 投放主动事件(character, ev):
    // 用现有 createWorldHook，type 标记为 'proactive'
    createWorldHook(data, {
        type: 'proactive',
        characterKey: character.key,
        eventId: ev.id,
        title: `${character.name}似乎在找你`,
        sourceText: ev.opening
    })
    // 在城堡动向/或专门入口推送一行提示，引导玩家去查看
    pushRow({ tag: '🔔', text: `${character.name}好像在找你。` })
```

**节制是重点**：`maxToday` 务必封顶（建议1，最多2）。宁可玩家觉得"难得有人来找我，很珍惜"，也不要"天天一堆人排队找我"。

## 六、双轨：本地模式 vs AI 模式（橘子明确要求两套都要）

玩家在设置里有开关：**对话模式 = 本地剧情 / AI 增强**（没填 API Key 时 AI 选项灰掉，默认落本地，保证开箱即玩、没网能玩）。

当玩家点开一个主动事件去互动时：

- **本地模式**：直接用 `ev.opening` + `ev.choices`，跟现有 encounters 的展示逻辑一样。
- **AI 模式**：把 `character.persona` 当 system prompt、`ev.aiSeed` 当本次相遇的种子、`world.memory` 里与该角色相关的条目当上下文，调 AI 生成对话。**复用 `ai/grader.js` 的请求模式**（走 `/api/ai-grade` 同款后端代理，key 只在后端，前端不碰）。
  - **关键降级**：仿照 grader「用户跳过/无key就返回null」——若 AI 不可用（无网/无key/报错），**自动回退到本地的 `ev.opening`**。玩家无感，关系照常推进。

**两套共用善后**：无论哪套生成对话，结束时都回写**同一套** `addAffinity` + `rememberWorldEvent` + `consumeHook`。这样玩家中途切换模式，关系是连续的。

## 七、实现顺序建议（分步交付，每步可单独验收）

1. **先搭骨架（纯本地）**：建 `characters/` + `_registry.js`，先做 2～3 个角色（如纳威、哈利、德拉科），各写 1～2 个 proactive 事件的本地文本。
2. **做调度器** `proactive-scheduler.js`，挂进 `nextDay()`，先用 `console.log` 打印"今天谁被触发了"验证逻辑。
3. **接 memoryTag**：在玩家关键行为产生 memory 的地方补 tag，让"有原因"这条真正生效。
4. **做投放与展示**：主动事件 push 进 hooks + 城堡动向提示 + 一个"有人找你"的入口让玩家点开互动（本地文本版）。
5. **验收节制**：连续推进多天，确认平均下来一天最多1～2人来、关系浅的几乎不来、不可预测。
6. **最后接 AI 增强层**：加 persona/aiSeed 的 AI 生成 + 降级回退，复用 grader 的请求与 key 管理。

## 八、给大克的验收标准

- [ ] 角色一文件一对象，静态人设/主动事件在文件里，动态状态在存档里（没把好感/memory写进角色文件）
- [ ] 调度器挂在 nextDay()，每天跑一次
- [ ] 主动事件必须有 memoryTag 对应的真实历史才会触发（无原因不弹）
- [ ] 一天主动事件总量封顶（1～2），有冷却，按好感阶段门槛过滤
- [ ] 有概率、有候选竞争，玩家无法精确预测
- [ ] 本地模式无网可玩；AI 模式失败自动降级回本地文本
- [ ] 两套都回写同一份好感+memory，关系连续
